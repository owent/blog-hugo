## 背景

为了支持云上可动态伸缩的代理，以及跨大区服务经公网通信，我之前对 [libatbus][1] 做了一轮改造。除了补上压缩和加密，还引入了拓扑路由，重新梳理了节点关系和多路连接。两篇设计文章分别介绍了 [libatbus 的路由与协议][3] 和 [libatapp 的连接管理与重连][4]。

上一次压测已经是十年前，测的是裸通道。现在游戏服务的 RPC 调用更频繁，一条消息里也常带着链路跟踪信息和更复杂的 RPC 元数据。这次我从 200 B 测起，跑完整的节点协议栈，看看不同包长下加密、压缩和通道选择会怎样影响收包速率。小消息会走合包路径，200 B 的 QPS 也包含了合包带来的收益。更小的消息这次没有单独测。

## 测试方法与指标

2026 年 11 月 18 日的测试覆盖 5 档固定 payload（200 B、1 KiB、8 KiB、64 KiB、300 KiB）。3 套环境各跑 TCP 和共享内存两种数据通道，每套环境、每种通道有 22 种请求配置 × 5 档包长，主矩阵共 660 条记录。22 种配置包括无加密无压缩的基线、5 种单独加密、4 种单独压缩，以及 4 种压缩分别搭配 AES-128-GCM、AES-256-GCM 和 ChaCha20-Poly1305 的 12 种组合。2016 年那组数据使用不同硬件、不同包长和裸通道，留作历史记录。 [原始报告与复现命令][bench]

[打开完整性能对比表](2615-benchmark-matrix.html)。可以固定环境比较各算法，也可以固定算法比较六种环境与通道。五档包长并排显示，每格同时列出 QPS、吞吐量，以及有记录时的压缩后大小（%）。还可以加看 CPU、RSS 或相对于基线的吞吐量，点开读数可核对协商记录。

发送端和接收端各运行一个 `atbus::node`，都监听并广播地址。发送端主动建立控制连接，接收端回连建立独立数据连接。发送端持续调用 `send_data`，触发 8 MiB 发送缓冲区背压后等待写队列腾出空间，接收端忙轮询并检查消息序号。每组运行 15 秒，按秒采样，吞吐量、QPS 和 CPU 占用取去掉开头两个样本和结尾一个样本的均值。加密组在连接建立时使用 X25519 和 HKDF-SHA256，密钥刷新间隔为 24 小时，这里的速率覆盖连接建立后的数据传输。 [测试方法][bench] · [统计脚本][report-script]

- **QPS**是接收端每秒收到的 payload 消息数，不计控制帧。
- **吞吐量**按接收端每秒交付的原始 payload 字节数计算。本文用 MiB/s（1 MiB = 1,048,576 B），不含协议头和加密膨胀，也不扣除压缩掉的字节。
- 固定包长时，QPS 乘以每条消息的 payload 字节数就是 payload 字节吞吐量。比较不同包长时，同时看两项才能知道消息处理速率和数据处理速率各自如何变化。主矩阵的两项读数均取自 CSV，复测记录只给出吞吐量的地方注明 QPS 为换算值。
- **CPU 与内存**按收发进程分别记录。CPU 使用 user 和 system 时间，100% 约等于每秒使用一个逻辑 CPU 秒。内存取全程样本中的最高 RSS。
- **每 CPU 秒的吞吐量**用吞吐量除以收发两端 CPU 占用之和（两端都是 100% 时除以 2）。它反映这套忙轮询驱动下搬运数据所用的进程 CPU 时间，包含轮询、协议处理等成本。
- **压缩后大小（%）**以原始大小为 100%，计算式为「压缩后字节数 ÷ 原始字节数 × 100%」。例如，1,000 字节压缩为 250 字节，表中记为 25%，字节数减少 75%。发送端独立压缩生成的类 JSON 测试文本，原始大小和参与压缩的内容均排除开头的 8 B 序号。协议栈实际压缩的是 protobuf body，线上字节数还会受帧头、合包等影响。 [发送端实现][bench-send] · [统计脚本][report-script]

ZeroMQ 的压测工具分别测请求应答的延迟和单向收包吞吐，吞吐同时报消息数和数据量。gRPC 的报告把单个在途请求的延迟、多个通道的饱和 QPS 和每服务端核心的吞吐分开。Aeron 的 AWS 报告进一步按包长给出延迟百分位，并用 p99 约束可用吞吐。我这里采用同样的区分，先看单通道打满时的消息速率和数据量，再看算法与 CPU、内存的取舍。将来要给跨区 RPC 做容量规划，还得在指定负载下测 RTT 和尾延迟。 [ZeroMQ 延迟工具][zmq-lat] · [ZeroMQ 吞吐工具][zmq-thr] · [gRPC Benchmarking][grpc-bench] · [Aeron AWS 压测指南][aeron-bench]

这轮压测也修了两个会改变结果的问题。早期发送端没监听，接收端回连拿不到正确的对端地址，压测流量落到了控制连接上。两端都监听后重新跑了矩阵。另一个问题是 `io_stream` 成功读取后没有清零空读计数，高频轮询下偶发的空读累积起来会触发误断连。3.0.1 把它改成只统计连续空读。 [复测记录][bench] · [3.0.1 变更记录][changelog]

报告记载了序号异常出现在预热阶段。CSV 的 `errors` 和 `seq_gaps` 列来自整次运行的计数，部分组合仍有非零值。本文引用裁剪窗口里的速率，保留这些计数的统计范围，不从汇总 CSV 推断异常发生的具体时刻。 [汇总 CSV][raw-data] · [统计脚本][report-script]

还有一处报告和 CSV 的差异。接收工具在首个带连接对象的收包回调里记录该连接的加密和压缩算法。三套 TCP 矩阵和 Linux 共享内存矩阵的记录与请求相符。WSL2 和 Windows 的共享内存矩阵各有 **105 条**请求了加密或压缩，协商列却全是 `none/none`。还需要逐连接收包和协商日志才能判断数据走了哪条路径、转换是否生效。完整表保留这些记录并标明差异，正文用这两套共享内存矩阵的基线比较通道。 [接收端实现][bench-recv] · [WSL2 共享内存 CSV][wsl-shm] · [Windows 共享内存 CSV][windows-shm]

### 压缩后的大小与处理速率

本次发送的是可压缩的类 JSON 文本。数据转换消息的 protobuf body 达到 1,024 B 才会尝试压缩。200 B 的各配置都走未压缩路径，运行速率集中在约 343～347 万条/s（655～663 MiB/s）。从 1 KiB 档位开始，才能用本组速率对比实际启用压缩的开销。 [压缩条件与测试方法][bench] · [Linux TCP 汇总 CSV][linux-tcp]

LZ4 default 把样本压到约 44%，无加密时的吞吐是基线的 47%。加上 AES-128-GCM 后，吞吐在 LZ4 default 上下降约 3%，在不压缩时下降约 11%。协议栈先压缩再加密，且两项处理会共同竞争收发路径上的 CPU，不能把分别测得的吞吐降幅直接相加。几百分点的差异还要结合批次波动看。例如 zstd 两档在 64 KiB 的吞吐接近，到了 300 KiB，无加密时 level 6 的样本比 level 3 低约 7%。 [Linux TCP CSV][linux-tcp]

跨大区时，我会同时看两个上限。一是机器每秒能处理多少原始 payload，二是链路每秒能承载多少原始 payload。若链路带宽为 $B$，实际线上字节数与原始 payload 字节数之比为 $r$，链路对应的 payload 上限约是 $B/r$。压缩会改变两个上限，实际吞吐还受 RTT、队列和并发影响。需要用业务报文测 $r$，尤其是已经压过的资产或二进制数据。

## CPU 与内存开销

忙轮询时两端 CPU 经常各接近 100%，直接比较 CPU 百分比很难看出同样时间能传多少数据。Linux TCP 的 64 KiB 样本里，无加密无压缩时每 CPU 秒交付约 **1,245 MiB**。只打开 AES-128-GCM 后约为 **1,105 MiB**，LZ4 default 和 zstd level 3 分别约为 **582 MiB** 和 **247 MiB**。同样的总 CPU 时间里，zstd 组交付的 payload 约为基线的五分之一，同时测试文本能压到约四分之一。这组数据适合估计饱和时的资源取舍，低负载下需要单独测轮询和业务线程的开销。 [Linux TCP CSV][linux-tcp]

内存也会影响通道选择。以 64 KiB 的基线为例，默认共享内存段容量为 256 MiB，Windows 和 WSL2 两端的 RSS 各升到约 267～268 MiB。Linux 记录的增幅集中在发送端。下表每格按接收端 / 发送端列出进程峰值 RSS，单位为 MiB。估算系统实际物理内存时，共享页需要去重，段容量与触达、计入进程 RSS 的页数也要分别看。 [共享内存配置][bench] · [六组 CSV][raw-data]

## 部署场景的容量参考

- **同机小消息**。在主矩阵选择目标系统的 200 B 或 1 KiB，比较 TCP 和共享内存的 QPS，再核对 RSS。Windows 的 200 B 样本为 77.5 万条/s（147.7 MiB/s）和 108.8 万条/s（207.6 MiB/s），WSL2 同一包长的两条样本顺序相反。不同平台要用本机数据选通道。
- **同机大消息**。对照业务包长的 QPS、吞吐量和共享内存占用。Linux 的 4～64 KiB 可以参考同批次交错复测。Windows 在 64 KiB 的主矩阵里，共享内存由约 5,876 条/s（367.2 MiB/s）的 TCP 样本提高到 34,189 条/s（2,136.8 MiB/s），接收端峰值 RSS 同时增加约 256 MiB。
- **启用加密的 TCP**。在交互表中选择目标平台和包长，比较符合部署安全要求的配置。若同时考虑压缩，以同一加密配置分别查看无压缩、LZ4 和 zstd，再根据测试文本压缩后的大小和实测吞吐量判断哪些组合值得带到业务链路复测。
- **跨区或混合包长**。先用业务消息的包长分布和可压缩性构造压测流量。记录有效 QPS、payload 吞吐量、线上字节数、两端 CPU 和 p99，逐步提高发送速率，找出达到延迟目标时可持续的速率。回环矩阵提供单连接跑满时的参考，这一轮没有链路端到端的延迟数据。

## 总结

这次压测给我提供了单数据连接打满时的参考。小包看消息速率，大包还要看每秒搬运的字节数和每 CPU 秒的吞吐。同机部署时，我会按目标包长交错跑 TCP 和共享内存，并同时记录两端 RSS。跨区部署要在满足安全要求的配置上，用业务报文和真实链路量线上字节数。要估算 RPC 容量，我还需要补测连接与握手耗时、不同发送速率下的 p50/p95/p99、混合包长与多连接并发。 [构建、矩阵运行和报告生成命令][bench]

其实还有优化空间。我想按之前 [《面向 CPU 缓存命中率的 AC 自动机优化》][2] 的思路，看看收发路径上哪些访问能改善缓存局部性。这个以后慢慢来。
