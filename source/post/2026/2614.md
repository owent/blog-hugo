## 背景

以前陆陆续续看到些文章，说是很多经典的数据结构其实并不完全匹配现代化的大缓存硬件。
比如BTree有更好的缓存亲和性，所以其实强于平衡树结构（Rust语言标准库字典容器基于BTree的原因）。
比如说现代化很多CPU的L1 Cache Line是64字节。如果访问随机结构很容易下一跳错开了这个Cache Line，而连续结构反而由于命中缓存会有更高的效率。

我也想试试优化改造一些常见的底层数据结构，试试看效果。比如链表，LRU Map等等。
不过在开始通用的容器改造之前，我先拿我之前写的AC自动机做个实验。

这个AC自动机最早用于脏字过滤系统。所以会有一些扩展，比如跳过空白字符，忽略大小写等等。

最早的实现是完全离散的，启动时加载。然后跑嗯干到一个问题，就是对于超大号词表而言，进程启动加载要6-7s。
后来就改成简单得序列化dump文件，下次加载直接加载之前建好的树结构这种形式。省去建树，让启动加载缩短到1s以内。
实现见 <https://github.com/atframework/atframe_utils/blob/main/include/string/ac_automation.h> 。
但是这个实现在load建树的时候，仍然是动态分配出来的Tree Node。在大型工程里，很容易数据碎片化。同时为了兼容UTF-8。
创建了一个定长的UTF-8字符的数组，然后把UTF-8字符，固定占8个字节。其实英文场景大多只要一个字节，中文也只有3个。有很大的空间浪费。

那么这波实现主要有几个思路。

- 把字符编码成token，用数字。让文字更紧凑。
- Build完以后整颗树紧凑存储Tree Node以增加缓存命中率。通过二分来代替原来的字典搜索。
- 增加了字符的别名以进一步减少词表的大小。（比如 二和2 可以视为等同）
- 增加了边界规则以便减少误匹配。（比如SM是屏蔽字，但是SMS、smile是合法词）
- 加载和dump的内存结构几乎和搜索匹配的时候一样（还是会做大小端转换），这样load/dump会非常快。

实现见 <https://github.com/atframework/atframe_utils/blob/main/include/string/ac_automation_v2.h> 。

简单来就是数据变紧凑了（提升缓存命中率），功能也变多变复杂了。
那么在这种场景下 v2 版本测试的性能提升就一定大于缓存命中率优化本身带来的提升。

## ac_automation_v2 vs ac_automation 性能对比报告

词表：使用我们开源版本服务器框架 [atsf4g-co 内的脏字表 `install/resource/compliance/text_filter.acv2`][1]
环境：WSL2 Debian 13 (trixie)，g++ 14.2.0，**RelWithDebInfo（`-std=c++20 -O2 -g -DNDEBUG`）**，单线程，词表与二进制均在 WSL 原生文件系统
数据：4 次独立进程运行（逐轮交错，消除机器状态漂移）；冷启动取每轮 round 0 最优，稳态取 round 1..N 中位数最优，匹配取 5 轮中位数最优。

我们构造了碎片化的内容分配以模拟真实运行环境。

## 1. 测试对象与保真度

词表由 v2 镜像提供（老实现无法直接读取该格式）：

| 项 | 值 |
| --- | --- |
| 关键词数 | 49,824 |
| v2 节点数 / 符号数 | 232,031 / 7,999 |
| 最长关键词 | 76 token |
| nocase | 是 |
| skip token | 2,847 个（其中 2,783 个为多字节 UTF-8 token） |
| 边界规则 | 114 条（426 个成员 token） |
| 别名（replacement）规则 | 0 条 |
| v2 逻辑 payload | 6,627,890 B（+2,052 B 派生符号索引，不序列化） |

保真度验证（每轮运行内自动完成，8/8 通过）：

- **v2 侧**：从加载后的快照提取全部关键词、skip 集、边界规则与 keyword 边界选项，经公开 API 重建后 `build()` + `dump()`，与 `text_filter.acv2` **字节级一致**。匹配基准测的就是生产词表本身。
- **v1 侧**：同一关键词表 + `set_nocase(true)` + 全部 64 个单字节 skip token（v1 的 skip 集是 256 位位图，**无法表达 2,783 个多字节 skip token**）。构建→dump→load 回读后与内存构建的 v1 在抽样语料上匹配结果逐条一致。

## 2. 测试方法

**编译**：RelWithDebInfo 口径 `-O2 -g -DNDEBUG`。

**堆模型（对称作用于 v1/v2）** —— 模拟长期运行服务的碎片化，避免单功能基准"临近分配 + 缓存预热"带来的虚高命中率：

1. **预散布**：任何自动机工作之前，分配 1,200,000 个 32~256B 随机小块并随机释放 2/3 → 约 80 万个散布空洞 + 约 40 万个存活"屏障"块。v1 的 45.5 万个节点/红黑树结点分配落入随机地址的空洞，与无关存活对象交错；v2 的快照是少数几个大块连续内存，基本不受影响（这正是紧凑存储的设计价值）。
2. **构建期扰动**：每插入一条关键词伴随一次随机小块分配/回收（模拟词表加工流水线的其他分配），v1/v2 对称。
3. **语料多样性**：匹配语料 **5000 条/组，且每轮重排顺序**——真实服务不会反复扫同一批文本，连续调用应命中不同的 trie 路径；固定顺序的小语料会把 trie 路径预热在缓存里，读数偏高。

**运行**：4 次独立进程运行逐轮交错；`malloc_trim(0)` 只在阶段计时结束后做 RSS 采样前调用（会引发后续轮次缺页，不能放在轮次之间）。

## 3. 构建 + 落地配置 / Load

冷启动口径（4 次运行取最优 round 0）：

| 阶段 | v1 | v2 |
| --- | --- | --- |
| 配置（仅 v2） | — | 1.8 |
| insert_keyword × 49,824 | 124.4 | 146.9 |
| init 失败指针（含在首次 dump） / build() | 270.1 | 152.1 |
| dump 序列化 | 155.7 | 3.9 |
| **合计** | **570.4** | **304.7**（v2 快 1.87x） |

![Build 与 Load 对比](2614-chart_build_load.png)

Load 配置文件（冷启动，CPU ms）：

| 口径 | v1 | v2 |
| --- | --- | --- |
| 文件流（生产路径） | 187.63 | 41.45¹ |
| 文件流 + verify_semantics（compliance 实际配置） | — | 19.36¹ |
| 内存镜像（纯反序列化+分配） | **190.38** | **3.93**（48.5x） |

解读：

- **v1 的开销遍布所有遍历类操作**：45.5 万节点散布在碎片空洞后，insert（124.4 ms）、失败指针 BFS（270.1 ms）、dump 序列化（155.7 ms）、load（190.4 ms）都为局部性买单。
- **v2 的开销集中在收集期分配**：insert/build 的 146.9/152.1 ms 主要是 collecting builder 的临时结点分配；其**最终快照的序列化与反序列化几乎与堆状态无关**（dump 3.9 ms，内存镜像 load 3.9 ms）——冻结表是少数几个大块连续内存。
- ¹ **v2 文件流 load 的 41.5 ms 是本报告未定论的异常**：同进程同词表的内存镜像 load 仅 3.9 ms，且 +verify_semantics（读同一文件、做更多事）反而只要 19.4 ms，更像 I/O/页缓存回写与分配器状态叠加的噪声。处理方式：热重载建议用字节缓冲路径（span 版 `load()`，3.9 ms）；启动时一次性文件 load 的绝对成本也远低于 v1。此现象值得后续单独定位。

## 4. 过滤/匹配（CPU 耗时）

语料：4 组 × 5000 条，确定性生成。短文本 ≤15B（平均 9.5B/12.1B），长文本恰 300B。hit 语料各嵌入 1 个真实敏感词并经重建 v2 验证命中（位置随机）；干净语料经重建 v2 验证零命中。v2 使用与 `task_action_filter_text.cpp` 相同的模式（复用 vector + `match_context`，默认 UTF-8 分词、非重叠）；v1 使用其唯一 API `ac_automation::match()`。

| 语料 | v1 match | v2 match | v2 contains | v2/v1 |
| --- | --- | --- | --- | --- |
| 短·无敏感词 (≤15B) | 533 ns | **481 ns** | **473 ns** | 0.90x |
| 短·含敏感词 | 3653 ns | **929 ns** | **825 ns** | **0.25x** |
| 长·无敏感词 (300B) | 17341 ns | **16577 ns** | **15985 ns** | 0.96x |
| 长·含敏感词 | 21915 ns | **17658 ns** | **10392 ns** | **0.81x** |

（吞吐，长·无敏感词：v1 ≈ 17.3 MB/s，v2 ≈ 18.1 MB/s）

![匹配/过滤对比](2614-chart_match.png)

**模拟业务负载场景下 v2 在全部四个场景持平或反超**：v1 的节点散布在碎片空洞中，每次匹配都为指针追逐的局部性买单；v2 的连续快照不受影响。

此外也有功能性差：

- 命中数（5000 条含词语料）：v1 3878（短）/3485（长），v2 **5003/5129**——v2 的多字节 skip 桥接多抓 29%~47% 的敏感文本（v1 单字节 skip 位图做不到）。
- 误报：无敏感词语料上 v1 各 1~7 次误报（无边界规则），v2 **0**。

## 5. 内存与体积

进程末尾受控测量：`malloc_trim(0)` 后采样 RSS，同一基线，一次只驻留一个自动机。

| 项 | v1 | v2 |
| --- | --- | --- |
| 配置文件 | 5.83 MB | 6.32 MB |
| 堆内存占用（受控探针，`malloc_trim` 后 RSS 增量） | **83.0 MB** | **6.4 MB**（13.0x） |
| 其中：碎片化堆下的增量读数 | 39.0 MB | 6.3 MB |
| 与逻辑 payload 的关系 | 455,815 节点 ×（`shared_ptr` + `std::map` + 字符串 + 分配器开销） | 6.32 MB 冻结段表 + 2 KB 派生索引 |
| 节点数 | 455,815 | 232,031 |

![内存与体积对比](2614-chart_memory.png)

注：碎片化堆下 v1 的 RSS 增量读数只有 39 MB——不是 footprint 变小，而是节点**复用了预散布阶段释放的空洞**（这部分 RSS 计入了基线）。83 MB 的全新进程探针读数是容量规划的上界；它也说明真实碎片化堆里 v1 的实际成本由"空闲 holes 是否够大"决定，业务运行久了 hole 变碎，v1 会向连续分配的地址空间要新内存。不过这个词表也不会老reload，所以问题不大。

## 6. 结论与建议

1. **模拟业务负载场景（碎片化堆 + 5000 条重排语料）下，v2 在全部含敏感词场景反超 v1（1.24~3.93x），无敏感词文本持平 v2，误报为 0**。
2. **初始加载与内存优势显著**：内存镜像 load 口径下 v1/v2 差距 **48.5x**；build **1.87x**；常驻内存 **13x**。
3. "是否含敏感词"用 **`contains()`**：比 v1 match 快 2.11x（长·含敏感词），比 v2 match 快 41%。
4. v2 文件流 load 的 41.5 ms 异常（第 3 节¹）建议后续定位；在此之前，热重载走字节缓冲 `load(span)` 路径（3.9 ms）。启动时一次性文件加载即使按 41.5 ms 计，也仍比 v1 快 4.5x。
5. 若继续压 v2 匹配耗时，下一个优化点是每 token 归一化路径与子节点二分查找（当前 ~55 ns/字节）。

整体来说，还是比较客观的。其实之前 [《实现strong_rc_ptr(比shared_ptr更快的引用计数智能指针)》][2] 虽然是另一个思路方向，但是基础的原理是一样的。
