## 背景

为了支持云上可动态伸缩的代理，以及跨大区服务经公网通信，我之前对 [libatbus][1] 做了一轮改造。除了补上压缩和加密，还引入了拓扑路由，重新梳理了节点关系和多路连接。两篇设计文章分别介绍了 [libatbus 的路由与协议][3] 和 [libatapp 的连接管理与重连][4]。

上一次压测已经是十年前，测的是裸通道。现在游戏服务的 RPC 调用更频繁，一条消息里也常带着链路跟踪信息和更复杂的 RPC 元数据。这次我从 200 B 测起，跑完整的节点协议栈，看看不同包长下加密、压缩和通道选择会怎样影响收包速率。小消息会走合包路径，200 B 的 QPS 也包含了合包带来的收益。更小的消息这次没有单独测。

## 测试方法与指标

2026 年 11 月 18 日的测试覆盖 5 档固定 payload（200 B、1 KiB、8 KiB、64 KiB、300 KiB）。每个平台、每种数据通道各跑 22 种配置，共 110 组。配置包括无压缩的加密对照、无加密的压缩对照，以及 4 种压缩配置分别搭配 AES-128-GCM、AES-256-GCM 和 ChaCha20-Poly1305 的 12 种组合。2016 年那组数据使用不同硬件、不同包长和裸通道，留作历史记录。 [原始报告与复现命令][bench]

发送端和接收端各运行一个 `atbus::node`，都监听并广播地址。发送端主动建立控制连接，接收端回连建立独立数据连接。发送端持续调用 `send_data`，触发 8 MiB 发送缓冲区背压后等待写队列腾出空间，接收端忙轮询并检查消息序号。每组运行 15 秒，按秒采样，吞吐量、QPS 和 CPU 占用取去掉开头 2 秒和结尾 1 秒的统计窗口。握手和密钥交换发生在开头，不计入稳态速率。 [统计脚本][report-script]

- **QPS**是接收端每秒收到的 payload 消息数，不计控制帧。
- **吞吐量**按接收端每秒交付的原始 payload 字节数计算。本文用 MiB/s（1 MiB = 1,048,576 B），不含协议头和加密膨胀，也不扣除压缩掉的字节。
- **CPU 与内存**按收发进程分别记录。CPU 使用 user 和 system 时间，内存取全程样本中的最高 RSS。持续打满时收发端各接近用满一核，这组数据描述的是单数据连接的饱和速率。
- **压缩后占比**是生成的类 JSON payload 单独压缩后的大小除以原始大小。协议栈压缩的是 protobuf body，线上字节数还会受帧头、合包等影响。 [指标定义与统计脚本][report-script]

这轮压测也修了两个会改变结果的问题。早期发送端没监听，接收端回连拿不到正确的对端地址，压测流量落到了控制连接上。两端都监听后重新跑了矩阵。另一个问题是 `io_stream` 成功读取后没有清零空读计数，高频轮询下偶发的空读累积起来会触发误断连。3.0.1 把它改成只统计连续空读。 [复测记录][bench] · [3.0.1 变更记录][changelog]

报告记载了序号异常出现在预热阶段。CSV 的 `errors` 和 `seq_gaps` 列来自整次运行的计数，部分组合仍有非零值。本文引用裁剪窗口里的速率，保留这些计数的统计范围，不从汇总 CSV 推断异常发生的具体时刻。 [汇总 CSV 与图表][raw-data] · [统计脚本][report-script]

## TCP 回环基线

三套环境都使用 IPv4 TCP 回环。下图保留各平台主矩阵的运行配置。

| 环境 | CPU 与系统 | 构建 / 分配器 |
| --- | --- | --- |
| Linux 测试机 | Ryzen 9 9950X，PVE 来宾 8 vCPU，Debian 13 | GCC 14.2 `-O3` / mimalloc 2.1.9 |
| WSL2 | Ryzen 7 9700X，限制为 4 核 8 线程，Debian 13 | GCC 14.2 `-O3` / glibc |
| Windows 原生 | Ryzen 7 9700X，8 核 16 线程，Windows 11 | MSVC `/O2` / MSVC CRT |

![三个平台在五档 payload 下的明文 TCP 回环吞吐量](2615-tcp-platforms.echarts.json "{height=320px max-width=940px}")

*无加密、无压缩。横轴是等距排列的实测包长档位，折线连接离散测点。* [各平台汇总 CSV][raw-data]

Linux 测试机在 200 B 时收到 **347 万条消息/s**，吞吐为 663 MiB/s。增至 300 KiB 后，收包速率降到约 9,049 条消息/s，payload 吞吐升到约 **2.59 GiB/s**。一条连接每秒能收多少条消息、能搬多少数据，需要结合包长看。Windows 原生在这套配置下的回环吞吐明显较低，例如 64 KiB 为 367 MiB/s，Linux 测试机为 2,490 MiB/s。三条曲线同时包含 CPU、系统、编译器和分配器的差异。

### WSL2 分配器对照

同一套 WSL2 环境里，原报告交错运行 glibc 和 mimalloc 两组共 110 对配置，其中 85 对的 mimalloc 样本更快。下面是三个大包对照，单位为 MiB/s。 [分配器对照原表][bench]

| 配置 | glibc | mimalloc | 变化 |
| --- | ---: | ---: | ---: |
| 64 KiB，明文 | 1,343.9 | 2,252.7 | +68% |
| 300 KiB，明文 | 1,109.2 | 2,488.1 | +124% |
| 64 KiB，AES-128-GCM | 951.5 | 2,162.2 | +127% |

报告中 200 B 和受压缩计算限制的组收益较小。两套 Linux 环境都使用 mimalloc 时，明文 64 KiB 和 300 KiB 的 WSL2 样本达到 Linux 测试机的约 90% 和 94%，8 KiB 则只有约 53%。两台机器的 CPU 和核心配置仍有差异，TCP 回环也有批次波动，这组对照无法单独估计 WSL2 的虚拟化开销。 [分配器对齐数据][bench]

## 加密与压缩

### 小消息的加密开销

固定 200 B 的 payload，比较 Linux 测试机上六种配置的收包速率。这个档位合包已生效，数据消息未达到压缩阈值。

![Linux TCP 在 200 B 下各加密配置的 QPS](2615-crypto-200b.echarts.json "{height=305px max-width=940px}")

*无压缩，横轴以百万条消息/s 计。ChaCha20 和 ChaCha20-Poly1305 是报告中的两条不同实现路径。* [Linux TCP 汇总 CSV][linux-tcp]

200 B 下，AES-GCM 三种配置约为 **150～154 万条消息/s**，对比无加密的 347 万，下降约 56%～57%。到 64 KiB，AES-GCM 约为 2,180～2,221 MiB/s，对比同矩阵的明文基线低约 11%～12%。单条小消息承担的固定处理开销占比更大，200 B 比 64 KiB 更容易看出收包速率的变化。三种 AES Key 长度之间的差距在这组数据里较小。

这套 x86 构建上，裸 ChaCha20 在 64 KiB 约为 103 MiB/s，带认证的 ChaCha20-Poly1305 约为 1,664 MiB/s。这里比较的是 libatbus 在本次构建里的实现路径，数据涵盖了整条收发路径的开销。 [Linux TCP 汇总 CSV][linux-tcp]

### 压缩后的大小与处理速率

本次发送的是可压缩的类 JSON 文本。数据转换消息的 protobuf body 达到 1,024 B 才会尝试压缩，200 B 样本走未压缩路径。下图从 1 KiB 开始对比实际进入压缩路径的几档样本。 [压缩条件与测试方法][bench]

![Linux TCP 不同压缩配置的 payload 吞吐曲线](2615-compression.echarts.json "{height=340px max-width=940px}")

*无加密。LZ4 fast 和 default 数据接近，图中展示 default。zstd default 和 high-ratio 分别对应 level 3 和 level 6。* [Linux TCP 汇总 CSV][linux-tcp]

固定 64 KiB，可以把同一个 payload 的压缩后占比和接收吞吐放在一起看。右列在相同压缩配置上增加 AES-128-GCM。

| 压缩配置 | 压缩后占比 | 无加密（MiB/s） | AES-128-GCM（MiB/s） |
| --- | ---: | ---: | ---: |
| 无压缩 | 100% | 2,489.9 | 2,209.7 |
| LZ4 default | 43.7% | 1,168.0 | 1,134.4 |
| zstd level 3 | 23.8% | 502.1 | 498.3 |
| zstd level 6 | 21.0% | 502.7 | 497.7 |

LZ4 把 payload 压到原大小的约 44%，接收吞吐约为未压缩时的 47%。zstd level 6 把 payload 压到约 21%，这组样本里与 level 3 的吞吐接近。开启压缩后，协议栈加密处理的是压缩后的数据，表里叠加 AES-128-GCM 后的吞吐变化也小于未压缩时的变化。这里的几个百分点不足以给配置排出稳定名次。跨大区是否值得压缩，还得用业务 payload 和实际链路测线上流量、CPU 占用与延迟。 [Linux TCP 汇总 CSV][linux-tcp]

## 共享内存与 TCP

共享内存组仍通过 TCP 建立控制连接。接收端额外监听 `shm://` 地址，握手后发送端接入共享内存写端，消息改走单向的共享内存数据通道。加密和压缩仍由同一套节点协议处理。 [共享内存测试拓扑][bench]

Linux 的初次矩阵里，8 KiB 的共享内存样本约为 1,661 MiB/s，低于 TCP 的 2,148 MiB/s。两组数据来自不同批次。报告随后在同批次交替跑 TCP 和共享内存，每档各取三轮。折线取中位数，表格保留各轮读数。 [矩阵 CSV][raw-data] · [交错 A/B 记录][bench]

![Linux TCP 和共享内存在六档包长下的三轮中位吞吐量](2615-linux-shm-ab.echarts.json "{height=320px max-width=940px}")

*Linux 测试机，mimalloc，无加密、无压缩。每个点是同批次三轮的中位数，离散包长以等距刻度标出。*

| Payload | TCP 三轮（MiB/s） | 共享内存三轮（MiB/s） | 中位数之比 |
| ---: | --- | --- | ---: |
| 1 KiB | 1,324 / 1,329 / 1,309 | 1,462 / 1,387 / 1,367 | 1.05× |
| 4 KiB | 1,841 / 1,862 / 1,764 | 2,281 / 2,306 / 2,284 | 1.24× |
| 8 KiB | 1,939 / 2,035 / 1,528 | 2,626 / 2,621 / 2,536 | 1.35× |
| 16 KiB | 1,469 / 1,484 / 1,492 | 2,732 / 2,715 / 2,694 | 1.83× |
| 32 KiB | 1,662 / 1,674 / 1,672 | 2,764 / 2,724 / 2,763 | 1.65× |
| 64 KiB | 2,374 / 1,973 / 1,743 | 2,801 / 2,798 / 2,793 | 1.42× |

8 KiB 的对比在交错复测里反了过来，共享内存的中位吞吐量高 35%。64 KiB 的 TCP 三轮跨度为 1,743～2,374 MiB/s，共享内存则在 2,793～2,801 MiB/s。报告还记录了同机同配置的 TCP 跨批次差异可达约 ±30%～40%。比较相近的配置时，批次、重复次数和单轮读数比单条曲线的高低更有用。 [重复测量与波动记录][bench]

Windows 原生主矩阵里，8 KiB 和 64 KiB 的共享内存样本分别约为 TCP 样本的 **4.46 倍**和 **5.82 倍**。同机用共享内存有吞吐收益，也会改变内存占用。以 Windows 的 64 KiB 样本为例，默认共享内存段为 256 MiB，接收端采样峰值 RSS 由约 11.4 MiB 升到 267.4 MiB。RSS 是单进程驻留量，估算实际物理内存时，共享页需要去重。 [Windows TCP 汇总 CSV][windows-tcp] · [Windows 共享内存汇总 CSV][windows-shm]

## 总结

这次压测给我提供了单连接打满时的参考。同机通信可以用交错复测比较 TCP 和共享内存，再结合内存占用选通道。跨大区链路上，加密配置受安全要求约束，压缩则要结合业务样本和带宽重测。本次回环测试没有测跨机 RTT、业务处理延迟和多连接并发。

其实还有优化空间。我想按之前 [《面向 CPU 缓存命中率的 AC 自动机优化》][2] 的思路，看看收发路径上哪些访问能改善缓存局部性。这个以后慢慢来。
