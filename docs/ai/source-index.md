### 句式检查示例

下列是构造的编辑示例，改写所用的功能、机制和条件仍须由目标材料确认；只处理表中说明的问题，不批量替换句式。

| 模式与示例 | 应检查的问题 | 处理方式与应保留的反例 |
| --- | --- | --- |
| 泛化开场：“在数字化时代，缓存的重要性日益凸显。” | 是否交代了与文章有关的变化或问题 | 有缓存失效材料时，直接讨论失效后的回源请求；有时间与数据的增长趋势说明保留 |
| 口号标题：“从配置到交付”“先看清，再掌握”；From setup to success、First understand, then master | 是否能指认章节对象，是否只有覆盖感或邀约 | 按内容写“配置校验”“发布流程”及自然英文标题；正文“先校验配置，再启动服务”和数值范围保留 |
| 自问自答：“问题来了，如何让配置真正可控？答案很简单。” | 问句是否只制造悬念，答案是否重复前文 | 直接写校验对象、失败条件和结果；真实排障疑问、FAQ 和研究问题保留 |
| 伪纠正：“这不是一次配置修改，而是工程能力的升级。” | 被否定的判断是否有人提出，后一项是否有事实 | 写实际改动与影响；纠正“异步调用一定不会等待”等真实误解时保留否定和解释 |
| 递进包装：“不仅支持导入，更能导出。” | 两项能力是否需要层级评价 | 确有支持时写“支持导入和导出”，保留两项事实；有实际等级或范围递进时写清区别 |
| 因果串：“通过统一入口实现流程整合，从而全面提升效率。”；By doing A, …, thereby … | 每项结果有无机制、测量和条件，是否把目标写成结果 | 分别说明入口接收什么、执行什么；效率无实测时不补承诺。输入输出关系与已证实的因果保留 |
| 名词串与抽象搭配：“对配置校验能力进行实现，形成管理闭环。” | 谁执行什么操作，所谓闭环包含哪些反馈动作 | 按材料写“启动时校验配置，缺失必填项时返回错误”；控制系统闭环、名词化术语和正式名称保留 |
| 简易或全面承诺：“只需一键即可无缝接入所有工具。”；Just …、Simply …、Seamlessly … | 前提是否省略，数量、兼容范围和操作难度是否有证据 | 列实际配置步骤与已验证支持范围；“设置该参数即可启用功能”有明确前提和实现依据时保留 |
| 假权威与评价：“众所周知，这是可靠的最佳实践。”；Obviously …、It is well known that … | 权威来自何处，“可靠”由什么验证 | 补对应推导、来源和条件，或按证据写为作者判断；数学推导中的已说明关系和有来源的规范建议保留 |
| 空泛平衡：“机遇与挑战并存，最终取决于具体场景。”；It depends on your needs | 是否说明哪项需求会改变选择 | 写出成本、延迟、维护约束等实际变量及其影响；真实条件分支和有依据的负面判断保留 |
| 机械排比与复述：“更清晰、更高效、更可靠”；每段以“这意味着”“换句话说”重复结论 | 并列项是否是不同事实，解释是否新增例子、条件或推导 | 删同义评价与重复小结，写具体结果；步骤列表、不同能力和帮助理解的重述保留 |
| 事实关系混用：已知性能与兼容性都有问题，却写“问题不在性能，而在兼容性” | 是否把优先处理一项写成否定另一项，或把转折、递进当成否定 | 写“性能和兼容性都存在问题，当前优先处理兼容性”；“调用成功，但日志未完整写入”保留两项事实，不只换连接词 |
| 研发状态缩写：“缺证 IDE 暂不实施”“取得证据后更新状态” | 缺少什么、检查是否执行、依据来自哪里 | 按实际记录写出尚未核验的本地格式或待执行的检查；缺少真实样本、尚未验证、验证未通过分别说明，不据此推断不支持 |
| 数量与阶段混用：假设“总尝试次数最多 3 次，含首次调用”，却改成“最多重试 3 次” | 总次数、重试次数、结束和成功是否被混用 | 写“总共最多尝试 3 次；首次失败后最多再重试 2 次”；取消和失败也可结束任务，不能写成成功完成 |
| 入口制造差异：同一目标与操作分别标为“第一次使用”“开始第一次操作”“快速上手” | 名称是否对应目标，同一组选项是否重复呈现同一选择 | 指向“快速上手”就使用该名称；目标与操作都相同时合并，不因地址相同就合并下载、查看等不同操作 |
| 英文虚饰：The module facilitates the seamless orchestration of configuration validation | 修饰是否掩盖实际动作，分词短语是否补出无依据的结果 | 已知只负责配置校验时写 The module validates the configuration；启动时机未知时不补 at startup，准确角色说明中的 serves as 可以保留 |
| 作者判断被软化：“我暂时不采用，每次升级都要改调用方，维护成本太高”改成“仍有进一步优化空间” | 取舍、理由和判断强度是否消失 | 保留作者的维护成本判断；需要时收紧适用版本，不补中性赞扬或虚构故事 |

### 本轮规则审阅

本轮由用户要求融合上述 Obsidian 写作指导触发。对照原有规则，合并了事实关系、研发状态、数量与阶段、
英文表达、入口操作、作者判断和图注真实性等要求；标题、日常流程和验收条目同步调整，没有增加默认加载的长词表。
新写与改稿 Skill 继续引用 `AGENTS.md`，没有需要新增的任务独有流程；Claude 兼容入口继续导入主规范，
不在 Skill 或兼容提示中复制全局条款。

表中的构造例子用于核对处理方式与保留条件，不是模型测试输出。本轮审阅覆盖技术顺序、范围、真实纠正、
递进的两项事实、准确术语、引文及原始输出，以及状态和阶段不可互换等反例；没有实际文章改稿、模型对照生成、读者盲评或窄屏页面实测，
因此只确认规则表达与这些边界一致，不声称生成质量已经提升。

工程校验：两个文章 Skill 的规范校验、目录名称和描述长度检查通过；主副本与镜像的全部文件哈希一致。
主规范、来源索引及四个 Skill 主副本与镜像文件按仓库配置通过 Markdown 检查，入口引用和 `git diff --check` 通过。本轮没有修改文章、图表或样式，未运行 Hugo 和页面渲染。

## 更新与评估写作规则

更换主要写作模型、出现反复的改稿问题、增加语言或文体、重要来源修订时，重新核验。
也可每 3—6 个月复核；这是维护建议，不是研究结论。只维护影响实际写作的规则，不积累无关论文摘要。

1. 读取 `AGENTS.md`、相关 Skill、本索引和实际失败样例，确认要解决的是事实、语义、结构还是文风问题。
2. 从已有来源查新版本、勘误和后续研究，再检索近期原文及反例。可用 `LLM editing author voice semantic drift`、
   `AI generated versus AI edited text stylometry`、`中文 AI 润色 文体 同质化`，按当前年份和目标文体调整。
3. 记录链接、发表和版本日期、访问日期、阅读范围、语言、文体、模型、样本与限制。
   区分正式研究、预印本、编辑指南和社区经验；摘要不能代替方法核查，相关性不能改成因果。
4. 用代表性中文与英文文章、作者认可的旧文和失败样例比较新旧规则。加入准确术语、真实对比、必要警告等
   应保留的反例。新写固定材料，润色固定原稿；两类结果分开看，控制模型版本和可控制的生成设置。
5. 先查事实、语义和作者立场是否保留，再评理解效果、重复、语气及剩余人工修改量。
   有条件时隐藏输出版本请读者比较，并使用未参与调规则的样本复查；未做的评估明确记录。
   检测分数、句长或词频不替代这些检查，也不能用流畅度抵消事实退化。
6. 只合入有依据的最小修改，合并重复规则并保留例外。稳定规则写入 `AGENTS.md`；
   只有任务独有流程或触发边界改变才修改 Skill 并同步镜像，来源及限制留在本文件。
   验证 Markdown、引用、相对路径和 diff；规则效果变差时根据版本记录撤回对应修改。

每次更新在审阅记录中说明：触发问题、核对的来源与版本、规则增删原因、样本和评审方式、
实际结果、未执行检查及待复核问题。不要把调研历史和维护日期复制进常驻提示。
