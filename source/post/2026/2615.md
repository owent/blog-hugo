## 背景

为了支持云上可动态伸缩的代理，以及跨大区服务经公网通信，我之前对 [libatbus][1] 做了一轮改造。除了补上压缩和加密，还引入了拓扑路由，重新梳理了节点关系和多路连接。两篇设计文章分别介绍了 [libatbus 的路由与协议][3] 和 [libatapp 的连接管理与重连][4]。

上一次压测已经是十年前，测的是裸通道。现在游戏服务的 RPC 调用更频繁，一条消息里也常带着链路跟踪信息和更复杂的 RPC 元数据。这次我从 200 B 测起，跑完整的节点协议栈，看看不同包长下加密、压缩和通道选择会怎样影响收包速率。TCP（`io_stream`）通道对不超过 7,168 B（`ATBUS_MACRO_DATA_SMALL_SIZE`）的消息会走合包路径，合并上限约 64 KiB，因此 200 B 和 1 KiB 两档的 TCP 速率都包含合包收益；共享内存（`shm://`）通道逐条写入独立消息块，不做合包。更小的消息这次没有单独测。

## 测试方法与指标

2026 年 11 月 18 日的测试覆盖 5 档固定 payload（200 B、1 KiB、8 KiB、64 KiB、300 KiB）。3 套环境各跑 TCP 和共享内存两轮矩阵，每套环境、每轮矩阵有 22 种请求配置 × 5 档包长，主矩阵共 660 条记录。22 种配置包括无加密无压缩的基线、5 种单独加密、4 种单独压缩，以及 4 种压缩分别搭配 AES-128-GCM、AES-256-GCM 和 ChaCha20-Poly1305 的 12 种组合。2016 年那组数据使用不同硬件、不同包长和裸通道，留作历史记录。 [原始报告与复现命令][bench]

[打开完整性能对比表](2615-benchmark-matrix.html)。可以固定环境比较各算法，也可以固定算法比较六组环境与通道。五档包长并排显示，每格同时列出 QPS、吞吐量，以及有记录时的压缩后大小（%）。还可以加看 CPU、RSS 或相对于基线的吞吐量，点开读数可核对协商记录与异常说明。

发送端和接收端各运行一个 `atbus::node`，都监听并广播地址。发送端先主动建立 TCP 控制连接，注册完成后按通道类型与优先级建立独立数据连接：纯 TCP 模式下，服务端（接收端）检测到自身监听的双工地址会直接返回，由发送端（客户端）发起独立 TCP 数据连接；接收端同时监听单工 `shm://` 时，本机发送端按优先级接入共享内存写端，接收端也会向发送端反向发起一条数据连接。发送端持续调用 `send_data`，在 TCP 触发 8 MiB 发送缓冲区（`ATBUS_MACRO_IOS_SEND_BUFFER_LENGTH`）背压或共享内存触发 256 MiB 环形缓冲区（`ATBUS_MACRO_SHM_MEM_CHANNEL_LENGTH`）满队后等待排空，接收端忙轮询并检查消息序号。每组运行 15 秒，按秒采样，吞吐量、QPS 和 CPU 占用取去掉开头两个样本和结尾一个样本的均值。加密组在连接建立时使用 X25519 和 HKDF-SHA256，默认密钥刷新间隔为 **3 小时**（源码 `atbus_node.cpp` 中为 `std::chrono::hours{3}`，压测工具未覆盖该值；原报告笔误记为 24 小时），这里的速率覆盖连接建立后的数据传输。 [测试方法][bench] · [统计脚本][report-script] · [节点默认配置][node-src]

- **QPS**是接收端每秒收到的 payload 消息数，不计控制帧。
- **吞吐量**按接收端每秒交付的原始 payload 字节数计算。本文用 MiB/s（1 MiB = 1,048,576 B），不含协议头和加密膨胀，也不扣除压缩掉的字节。
- 固定包长时，QPS 乘以每条消息的 payload 字节数就是 payload 字节吞吐量。比较不同包长时，同时看两项才能知道消息处理速率和数据处理速率各自如何变化。主矩阵的两项读数均取自 CSV，复测记录只给出吞吐量的地方注明 QPS 为换算值。
- **CPU 与内存**按收发进程分别记录。CPU 使用 user 和 system 时间，100% 约等于每秒使用一个逻辑 CPU 秒。内存取全程样本中的最高 RSS。
- **每 CPU 秒的吞吐量**用吞吐量除以收发两端 CPU 占用之和（两端都是 100% 时除以 2）。它反映这套忙轮询驱动下搬运数据所用的进程 CPU 时间，包含轮询、协议处理等成本。若发送端 CPU 采样缺漏或跨多秒累计，该比值不再可靠，交互表对应单元格留空。
- **压缩后大小（%）**以原始大小为 100%，计算式为「压缩后字节数 ÷ 原始字节数 × 100%」。例如，1,000 字节压缩为 250 字节，表中记为 25%，字节数减少 75%。该列由发送端用命令行 `--level` 独立压缩生成的类 JSON 测试文本测得，排除开头的 8 B 序号；协议栈实际压缩的是 protobuf body，线上字节数还会受帧头、合包等影响。 [发送端实现][bench-send] · [统计脚本][report-script]

这轮压测先修了两个会改变结果的问题。早期发送端没监听，接收端回连拿不到正确的对端地址，压测流量落到了控制连接上，两端都监听后重跑了矩阵。另一个问题是 `io_stream` 成功读取后没有清零空读计数，高频轮询下偶发的空读累积起来会触发误断连，3.0.1 改为只统计连续空读。 [复测记录][bench] · [3.0.1 变更记录][changelog]

报告记载了序号异常出现在预热阶段。CSV 的 `errors` 和 `seq_gaps` 列来自整次运行的计数，部分组合仍有非零值。本文引用裁剪窗口里的速率，保留这些计数的统计范围，不从汇总 CSV 推断异常发生的具体时刻。 [汇总 CSV][raw-data] · [统计脚本][report-script]

### 核对源码后确认的三处测试偏差

把汇总 CSV 与当时代码对照后，有三个直接影响结论解读的偏差需要先交代清楚，避免把测试实现问题当成协议栈或算法本身的特性：

1. **共享内存通道按当前设计不协商加密与压缩，且 `linux_shm` 主矩阵 110 组实际运行在 TCP 上**。在 [`atbus_node.cpp`][node-src] 和 [`atbus_message_handler.cpp`][handler-src] 中，`shm://` 与 `mem://` 是单工通道，不设置 `kRegFd` 标志，不走 `NodeRegisterReq/Rsp` 双向握手，因此 `connection_context` 上的加密和压缩算法始终保持 `none/none`。这直接解释了 `wsl_shm` 和 `windows_shm` 两个矩阵的全部表现：110 组协商列全是 `none/none`、22 种加密与压缩组合的速率全部齐平、收发两端峰值 RSS 同步升到约 267～268 MiB（256 MiB 共享内存段）、且几乎全为 0 序号跳变。原报告称“加密/压缩在 shm 通道上照常协商生效”与当前实现不符。反观 `summary.linux_shm.csv`，尽管它与 `wsl_shm` 运行同一套编译产物，却呈现出五项属于 TCP 的特征：105 组非明文记录的协商列全与请求一致、吞吐随 `chacha20`（96.5 MiB/s）和 `zstd`（500.5 MiB/s）大幅下降并与 Linux TCP 矩阵逐项吻合、收发峰值 RSS 始终只有 14.8～15.6 / 23.0～39.5 MiB（没有 256 MiB 共享内存页）、64 KiB/300 KiB 发送端 CPU 保持 100%、且绝大多数记录有 10～47 次 `seq_gaps`。从源码看，`atbus_message_handler.cpp` 中服务端监听单工 `shm://` 时因 `is_duplex_address()` 为假，会先于 `NodeRegisterRsp` 向发送端反向发起一条 TCP 数据连接；一旦发送端先接入这条反向 TCP 连接，后续收到 `NodeRegisterRsp` 时就会因已有数据连接而跳过 `shm://`。此外 Linux SysV 共享内存退出仅调用 `shmdt()` 而不删段（[`channel_shm.cpp`][shm-src]），复用旧段时 `shm_attach()` 不会 `memset` 全部 256 MiB，数据不经 `shm://` 时两端 RSS 也不会上涨。由于这轮未保留原始 stderr 日志，无法另行排除脚本参数因素，但五项独立数据已能确认 `linux_shm` 主矩阵跑在 TCP 上。因此本文用同批次交错 A/B 复测评估 Linux 共享内存，不再把 `linux_shm` 矩阵当作共享内存数据。 [接收端实现][bench-recv]
2. **协议栈发送打包路径把压缩等级写死为 `kBalanced`**。[`atbus_connection_context.cpp`][context-src] 的 `pack_message_with()` 直接传入 `compression::level_t::kBalanced`，`node::conf_.compression_level` 从未传递到 `connection_context`。按 `atframe_utils` 的映射，`kBalanced` 在 LZ4 上对应 `LZ4_compress_fast(..., accel=6)`，在 zstd 上对应默认 `level 3`。而发送端工具测“压缩后大小（%）”时直接把命令行 `--level` 传给了压缩函数（LZ4 的 `fast`/`default` 均为 `accel=1`，zstd 的 `default`/`high-ratio` 分别为 `level 3` 和 `level 6`）。结果就是：本次矩阵里 `lz4@fast` 与 `lz4@default` 在线上跑的是同一档（`accel=6`），`zstd@default` 与 `zstd@high-ratio` 在线上跑的也都是 **`zstd level 3`**。原报告据此得出“zstd level 6 几乎没有额外 CPU 代价”并不成立，本文改为按请求预设名展示，并把线上速率与离线压缩率分开标注。
3. **共享内存大包（64 KiB / 300 KiB）存在发送端 CPU 采样缺漏**。[`benchmark_node_stream_send.cpp`][bench-send] 的 1 秒统计定时器只在 `node->poll()` 时触发，但内层洪泛循环只有在触发背压（`EN_ATBUS_ERR_BUFF_LIMIT`）或跑满 15 秒时才跳出。256 MiB 共享内存环在 64 KiB / 300 KiB 下接收端排空足够快，发送端几乎不触发背压，导致 `send.samples` 样本数不足 4 条，裁剪首尾后均值为 `0.0%`（`wsl_shm` 64/300 KiB 全部 44 组、`windows_shm` 38/44 组）；偶发跨多秒触发时则会把多秒累计 CPU 按 1 秒折算，出现 `647.6%`（`windows_shm` 64 KiB 明文）或 `129%～137%` 的异常读数。

这些差异与实际链接的密码库路径直接相关：

- **ChaCha20 与 ChaCha20-Poly1305 走不同后端**。在 `atframe_utils` 的 `crypto_cipher.cpp` 中，裸 `chacha20` 路由到 **libsodium**（`crypto_stream_chacha20_xor_ic`），并非原报告说的 OpenSSL 路径；而 `chacha20-poly1305-ietf` 在启用 OpenSSL 1.1+ 或 LibreSSL 2.4+ 时优先匹配 `EN_CIMT_CIPHER`（走 OpenSSL 3 或 LibreSSL）。此外 `cipher::init_global_algorithm()` 只做了 OpenSSL 初始化，没有调用 `sodium_init()`，未在业务侧显式初始化时 libsodium 的运行期 SIMD 检测不会启用。
- **Linux/WSL2（OpenSSL 3）**：在支持 AES-NI 的 x86 CPU 上，AES-GCM 三个 Key 长度在 64 KiB 和 300 KiB 差距很小（8 KiB 的分散受回环批次波动影响，要区分 Key 长度本身还需交错复测），`ChaCha20-Poly1305` 居次，裸 `ChaCha20` 落到约 100～112 MiB/s。
- **Windows（LibreSSL 4.4.0）**：全部五档包长均为 `ChaCha20 > ChaCha20-Poly1305 > AES-128/192-GCM > AES-256-GCM`。到 300 KiB 差距更明显：`ChaCha20` 为 162.1 MiB/s、`ChaCha20-Poly1305` 为 121.7 MiB/s，而 `AES-128-GCM` 和 `AES-256-GCM` 分别只有 78.0 和 73.5 MiB/s（仅为明文 551.8 MiB/s 的 14% 和 13%），且 200 B/1 KiB 上 `AES-128-GCM > AES-192-GCM > AES-256-GCM` 呈阶梯下降。这反映的是当前 Windows LibreSSL 构建产物上的实测表现，跨平台选型必须按目标环境实际链接的密码库验证，不能直接套用 Linux 的排序。

Windows TCP 64 KiB 上出现了另一种现象：因为本机回环拷贝和 LibreSSL 加密开销都很高，开启 LZ4 把待加密和待写入内核的数据缩减一半以上后，**原始 payload 吞吐反而高于不压缩**。明文从 367.2 MiB/s 升到 416.3～437.5 MiB/s；`AES-128-GCM` 从 134.6 MiB/s 升到 273.3～294.8 MiB/s（超过 2 倍）；`ChaCha20-Poly1305` 从 182.8 MiB/s 升到 428.1～432.1 MiB/s（约 2.35 倍，高于 Windows 明文 TCP）。300 KiB 上 `AES-128-GCM + LZ4` 也是无压缩 `AES-128-GCM` 的 3 倍以上（253.3～258.5 vs 78.0 MiB/s）。 [Windows TCP CSV][windows-tcp]

跨大区部署时，可以同时估两个上限：一是单连接 CPU 每秒能处理多少原始 payload，二是网络链路每秒能承载多少原始 payload。若链路可用带宽为 $B$，实际线上字节数与原始 payload 字节数之比为 $r$，链路对应的 payload 上限约是 $B/r$。按 Linux 64 KiB 读数和本测试文本的可压性做一个忽略帧头和 RTT 的粗估：

- **1 Gbps 跨区专线（理论线速约 119 MiB/s）**：不压缩时链路先打满；开 LZ4（$r \approx 0.44$）后链路侧 payload 上限约 271 MiB/s，远低于 `LZ4 + AES-128-GCM` 单核约 1,134 MiB/s 的 CPU 上限；开 zstd `level 3`（$r \approx 0.24$）后链路侧上限约 497 MiB/s，刚好接近 `zstd + AES-128-GCM` 单核约 498 MiB/s 的处理能力。
- **10 Gbps 内网链路（理论线速约 1,192 MiB/s）**：不压缩的 `AES-128-GCM`（约 2,210 MiB/s）在收发各占一核时已经超过万兆线速；开 `LZ4 + AES-128-GCM`（约 1,134 MiB/s）接近线速但瓶颈转向 CPU；开 `zstd + AES-128-GCM`（约 498 MiB/s）会明显受单核 CPU 限制，只有在多连接共享紧缺带宽时才划算。

以上只用本测试文本的压缩率做量级参考，实际吞吐还受 RTT、发送缓冲区与并发流数影响，上线前仍要用真实业务报文实测 $r$（特别是已压缩资源或高熵二进制数据）。

使用共享内存前还要注意功能边界：按当前实现，`shm://` 通道**不支持加密也不支持压缩**，适合同机可信进程的明文高吞吐通信；如果业务要求同机通信也必须加密，需要走 TCP/Unix Socket 通道或等后续协议支持。

## CPU 与内存开销

忙轮询时两端 CPU 经常各接近 100%，直接比较 CPU 百分比很难看出同样时间能传多少数据。Linux TCP 的 64 KiB 样本里，无加密无压缩时每 CPU 秒交付约 **1,245 MiB**；只打开 AES-128-GCM 后约为 **1,105 MiB**；LZ4（`kBalanced` / `accel=6`）和 zstd（`kBalanced` / `level 3`）分别约为 **582 MiB** 和 **247 MiB**。同样的总 CPU 时间里，zstd 组交付的 payload 约为基线的五分之一，同时测试文本能压到约四分之一。这组数据适合估计饱和时的资源取舍，低负载下需要单独测轮询和业务线程的开销。对于 `wsl_shm` 和 `windows_shm` 的 64 KiB、300 KiB 记录，因发送端 CPU 采样为 `0.0%` 或跨秒累计异常（如 `647.6%`），不再计算每 CPU 秒吞吐量。 [Linux TCP CSV][linux-tcp]

内存也会影响通道选择。默认共享内存段容量为 256 MiB（`ATBUS_MACRO_SHM_MEM_CHANNEL_LENGTH`），真实走了共享内存的 WSL2 和 Windows 两端进程峰值 RSS 都从约 11～26 MiB 升到约 267～268 MiB。`summary.linux_shm.csv` 的 14.8 / 33.2 MiB 反映的是回落到 TCP 后的进程内存，不是挂载并读写 256 MiB 共享内存段的实际占用。下表每格按接收端 / 发送端列出 64 KiB 基线的进程峰值 RSS，单位为 MiB。估算宿主机物理内存时，两个进程映射的同一段共享内存物理页需要去重，不会消耗双倍物理内存。 [共享内存配置][bench] · [六组 CSV][raw-data]

## 同类通信库测试对照与可补充项

对比业界常用的通信与 IPC 基准测试——包括 ZeroMQ（`local_lat` / `local_thr`）、gRPC Benchmarking、Aeron AWS 压测指南、NATS（`nats bench`）以及 Eclipse iceoryx2——能更清楚地定位 `libatbus` 当前这套压测覆盖了什么、还缺什么。 [ZeroMQ 延迟工具][zmq-lat] · [ZeroMQ 吞吐工具][zmq-thr] · [gRPC Benchmarking][grpc-bench] · [Aeron AWS 压测指南][aeron-bench]

{{< dom html.class="table-responsive" html.role="region" html.aria-label="同类通信库基准测试维度对照" html.tabindex="0" >}}

| 测试维度 | 同类通信库常见做法 | libatbus 本轮现状 | 缺口影响 |
| --- | --- | --- | --- |
| 延迟与尾延迟 | ZeroMQ 单独测 RTT；gRPC / Aeron 在固定发包速率（开环）下用 HdrHistogram 报 p50 / p99 / p99.9 | 未测延迟，仅测闭环满载单向吞吐 | 无法评估小包合包引入的排队延迟，也不能按 p99 倒推 RPC 可用容量 |
| 线上真实流量 | 区分应用层 payload 吞吐与链路层 wire 字节数 | 仅计 payload 吞吐；压缩率由发送端离线另算 | 无法直接验证帧头、protobuf 封装、IV/Tag 膨胀以及压缩后的真实省流比例 |
| 并发与拓扑 | NATS 测多发布/多订阅扇出；gRPC 测多通道与每核 QPS；iceoryx2 测 1 对 N 共享内存 | 仅 1 对 1 单数据连接直连 | 未覆盖 libatbus 特色的 N 对 1 汇聚、1 对 N 广播与代理多跳中继成本 |
| 网络环境 | gRPC / Aeron / NATS 均区分本机与跨机真实网卡/广域网 | 全在本机回环执行 | 回环掩盖了跨区带宽受限下压缩的真实收益，还放大了回环批次双稳态 |
| 语料与负载形态 | 混合包长、低/中/高负载曲线、不可压缩语料 | 固定单一包长 + 可压缩类 JSON + 100% 忙轮询 | 未测高低包长混跑、高熵二进制数据触发压缩跳过，以及低载休眠时的 CPU/延迟折中 |
| 握手与密钥轮换 | gRPC 将 TLS 建连速率与稳态流吞吐分开测试 | 握手被丢弃在 2 秒预热窗口外，15 秒内无重协商 | 缺少 X25519 + HKDF-SHA256 建连峰值与 3 小时密钥轮换时的抖动数据 |
| 统计与防呆 | 绑核隔离、多轮交错取中位数与分位区间、运行时校验有效路径 | 主矩阵单轮跑完，缺少对真实通道与压缩档位的断言 | 导致 `linux_shm` 回落 TCP、压缩写死 `kBalanced`、`send_cpu=0%` 未被及时拦截 |

{{< /dom >}}

结合 `libatbus` 的服务网格与跨大区通信定位，下一轮压测最值得优先补齐五块内容：

1. **开环控速延迟测试（规避协调遗漏）**。闭环一发一收（ping-pong）在系统出现短暂停顿时会自动放慢发包，从而漏记排队延迟（Coordinated Omission）。参考 Aeron 与 gRPC 的做法，按目标速率（如饱和 QPS 的 30%、50%、70%、85%）定频打入带单调时钟戳的消息，用 HdrHistogram 记录单向或 RTT 的 p50/p95/p99/p99.9，重点对照 200 B / 1 KiB TCP 合包与 `shm://`、以及忙轮询与事件休眠驱动下的尾延迟差异。
2. **线上真实字节数与混合/不可压缩语料**。在 `connection` 层统计实际写入 socket 或共享内存的 wire bytes，与 payload bytes 并排汇报，直接给出加密膨胀率与压缩实测省流率；同时增加游戏典型混合包长分布（如 80% 的 64～256 B 小包混 20% 的 4～64 KiB 大包）和随机/已压缩二进制负载，验证 `_allow_compress()` 跳过不可压缩消息时的额外 CPU 损耗。
3. **多连接并发、扇入扇出与多跳代理转发**。`libatbus` 的核心场景不只是点对点直连，还包括网关汇聚（N→1）、广播（1→N）和经过上游或代理节点的 2 跳/3 跳转发。补齐多节点拓扑和单节点多连接扩展测试，才能看到事件循环、路由查表、缓冲池与 `shm://` 多段并发在真实拓扑下的表现。
4. **跨机网卡与模拟广域网（`tc netem`）**。在两台独立机器上跑 1 Gbps / 10 Gbps 网卡实测，并用 `tc netem` 叠加跨区常见 RTT（如 50 ms / 150 ms）、抖动与 0.1%～1% 丢包，同时检验 8 MiB 发送缓冲区在高带宽延迟积（BDP）链路下是否成为瓶颈，以及 LZ4/zstd 在带宽受限时的真实端到端加速比。
5. **压测框架防呆与建连/轮换专项**。在压测脚本里加入强制断言：校验实际收包连接的协议 scheme（避免 `shm://` 静默回落 TCP）、校验协商算法与实际压缩等级、校验采样点数避免 `send_cpu=0%` 混入报表；对关键对比项统一使用绑核 + 同批次多轮交错并输出中位数与离散区间；另起轻量专项测 X25519 握手建连速率与密钥轮换时的 p99 抖动。

## 总结

这次压测和逐项核对代码，既拿到了单数据连接打满时的跨平台参考，也顺手揪出了几处容易误导结论的实现细节：共享内存单工不协商加密/压缩且 Linux 共享内存主矩阵回落到了 TCP、发送路径把压缩档位写死为 `kBalanced`、Windows 链接 LibreSSL 后加密排序与 Linux 完全相反、以及无背压下发送端 CPU 定时器缺采。把这些边界摊开讲清楚，数据才真正能拿来指导选型。

小包看消息速率和合包行为，大包看原始 payload 吞吐、每 CPU 秒吞吐和内存分配器开销；同机明文大包优先考虑共享内存并留意 256 MiB 内存段占用，跨区链路则围绕安全要求、真实业务压缩率和带宽上限权衡算法。下一步除了修掉上述几处代码和压测脚本问题，还需要按同类通信库的基准方法补齐开环控速 p50/p95/p99 延迟、线上 wire 字节统计、多连接与多跳代理拓扑、跨机广域网模拟以及建连与密钥轮换测试。 [构建、矩阵运行和报告生成命令][bench]

其实协议栈本身还有不少优化空间，比如 `pack_message_with()` 在不压缩时仍无条件预留 `compressed_buffer`，后续也可以按之前 [《面向 CPU 缓存命中率的 AC 自动机优化》][2] 的思路，继续排查收发热路径上的缓冲区分配和缓存局部性。这些以后慢慢来。
